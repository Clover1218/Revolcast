# Revolcast 开发文档 · 服务器状态查询闭环方案

本文档定义「MC 服务器在线状态采集 + QQ 指令查询」这一闭环的设计与实现约定。

- 基准文档：《鹊桥与服务端WS连接格式详解》（下行 `send_rcon_command`）、《Websocket消息结构设计文档》（下行指令与回执）、《Revolcast_数据库表设计文档_v1.1》§5（Redis 键命名族）。
- 涉及业务：新增 **BIZ-012 查询服务器在线状态**。

---

## 1. 背景与目标

现状：Backend 与 MC 服务器（鹊桥）之间已有 WS 长连接（per-server API Secret 鉴权），上行只消费玩家事件，下行 `send_private_msg` **不等待回执**。因此后端完全不知道某台服务器此刻有多少人在线。

目标：

1. 对**每一个在线（已建立 WS 连接）的 MC 服务器**，每分钟主动执行一次 `list uuids`，把结果落到 Redis。
2. 提供 QQ 私聊指令 `revolcast server <code> status`，**只读 Redis** 返回该服务器的在线人数与玩家昵称。

非目标：

- 不落 PostgreSQL / MongoDB（高频、无审计价值、可随时重建）。
- 不做历史曲线、不做进服/离服流水（`game_events` 已承担审计职责）。
- 本期不把状态推送给 Web 前端（见 §14 扩展点）。

---

## 2. 已确认的设计决策

| # | 决策 | 取值 | 理由 |
| :-- | :--- | :--- | :--- |
| D1 | 键粒度 | 每服一个 String 键，JSON value | 写入 1 条命令、读取 1 条命令；过期语义交给 Redis 原生 TTL，无残留 |
| D2 | 键的定位字段 | `server_code`（不是 `server_id`） | WS 连接侧与 QQ 指令侧**都只有 code**，读写两侧都不需要 code→id 映射，做到零查表 |
| D3 | 断连语义 | WS 连接注销时**立即 DEL 键** | 只有当前在线的服务器才有状态键；查询统一回落「未找到」，不区分「从未上线 / 刚掉线」 |
| D4 | 实时性 | 纯 60s 轮询，查询不触发即时拉取 | QQ 端零等待，RCON 压力恒定；最长滞后 60s，对「有多少人在线」这个语义可接受 |
| D5 | 回显格式 | 只支持英文原版格式 | 见《鹊桥》文档「发送RCON命令」示例；服务端 locale 若改为中文将解析失败（§6.4 已定义降级行为） |

## 3. 总体流程

### 3.1 采集链路（每连接一条，60s）

```
MC 服务端（鹊桥 WS，已鉴权 server_id + server_code）
        ▲                                   │
        │ ① send_rcon_command                │ ② post_type=response
        │    data.command = "list uuids"     │    echo 原样回传
        │    echo = "rcon:<唯一ID>"          │    data = "There are 3 of a max of 20 ..."
        │                                   ▼
  transport.GameServerClient  ── ③ echo 关联（不进业务队列）
        │
        ▼ ④ protocol.ParseListUUIDsEcho
  biz.GameStatusService.RecordListUUIDs
        │
        ▼ ⑤ Redis SET revolcast:server:status:{server_code}  TTL=3×间隔
```

### 3.2 查询链路（一次 GET）

```
QQ 私聊 "revolcast server <code> status"
  → handler.parseCommand → commandServerStatus
  → biz.GameStatusService.GetStatus(ctx, code)      // 1 次 Redis GET，0 次查表
  → 命中：渲染「当前服务器有 N 人：…」；未命中：「未找到，请联系管理员」
```

## 4. Redis 键值设计

### 4.1 键与值

| 项 | 取值 |
| :--- | :--- |
| 键 | `revolcast:server:status:{server_code}` |
| 类型 | `String`（JSON 文档） |
| 写入 | `SET key value EX 180`（单条命令，整体覆盖，**无读改写**） |
| 读取 | `GET key` → `json.Unmarshal` |
| TTL | `3 × 采集间隔`，默认 **180s**（由代码计算，不单独配置） |
| 删除 | WS 连接注销时 `DEL`；TTL 作为兜底 |

```json
{
  "server_id": 1,
  "server_code": "survival",
  "online": 3,
  "max_players": 20,
  "players": [
    { "nickname": "Bot1", "uuid": "51a4b33d-8b80-3bde-806f-de4086b03058" },
    { "nickname": "Bot2", "uuid": "16beaa94-ff1b-37a7-8afb-c22dcb8c16d1" },
    { "nickname": "Bot3", "uuid": "73f370b4-497b-347a-a6bb-50d07eb88947" }
  ],
  "updated_at": "2026-10-23T13:29:00.000Z",
  "source": "rcon"
}
```

字段约定：

| 字段 | 说明 |
| :--- | :--- |
| `server_id` | 连接已鉴权的 `game_servers.id`，**仅作冗余标识**，不参与键定位 |
| `server_code` | 与键后缀一致，便于值自解释（排查时不用回看键名） |
| `online` | 取自回显头部的 `N`（`There are N of a max of M ...`），**不是** `len(players)` |
| `max_players` | 回显头部的 `M` |
| `players` | 解析出的昵称与 UUID，顺序与服务端回显一致 |
| `updated_at` | 采集成功时刻，UTC 固定毫秒，复用 `protocol.FormatEventTime`；**只用于展示/排查，不参与过期判断** |
| `source` | 固定 `rcon`，为将来引入其他采集方式（如 query 协议）留出区分点 |

### 4.2 为什么用 `server_code` 而不是 `server_id`

- **写入侧**：`GameServerClient` 持有 `serverID` 与 `serverCode`，两者都可以做键，无差别。
- **读取侧**：QQ 指令只拿到用户输入的 `code`。若键用 `server_id`，必须先把 code 映射成 id —— 要么查 `game_servers`（违背「少查表」），要么再维护一份 code→id 缓存（多一个键、多一次 GET、多一处一致性负担）。
- **稳定性**：`game_servers.code` 有 UNIQUE 约束，且 `UpdateGameServer` **不允许修改 code**（只改 name/description/status），停用是软删、code 不复用。因此用 code 做键不会出现「键指向已变更实体」的问题。

> 数据库设计文档 §5 曾预留 `revolcast:server:{server_id}:heartbeat`（未实现）。本次落成 `revolcast:server:status:{server_code}`，并同步修订 §5 该行，说明「以 code 定位以避免查询侧反查 id」。

### 4.3 读写成本

| 路径 | Redis 命令数 | DB 查询数 | 量级 |
| :--- | :--- | :--- | :--- |
| 单台服务器单次采集 | 1 × `SET`（含 TTL） | 0 | 每服每分钟 1 次 |
| 一次 QQ 状态查询 | 1 × `GET` | 0 | 用户触发 |
| 断连清理 | 1 × `DEL` | 0 | 每连接一次 |

100 台服务器 = 100 个键、每分钟 100 次 SET、总内存约 20KB（按 3 人/服估算）。无扫描、无 `KEYS`、无 `MGET` 全量。

### 4.4 失效与新鲜度

- **正常**：每 60s 被新值整体覆盖，`updated_at` 随之推进。
- **采集停摆**（进程崩溃 / 网络中断 / 服务器掉线）：
  - 连接注销路径会立即 `DEL`；
  - 若进程整体崩溃（没有注销机会），TTL 180s 内必然过期；
  - 两种情况最终都表现为「键不存在」→ 查询回落「未找到」。
- **不做「可能已过期」提示**：TTL 已保证最长 180s 的残留，再叠加提示文案只会增加噪音。若将来把 TTL 放宽到 10 分钟以上，才需要引入 `updated_at` 相对当前时间的过期提示。

### 4.5 失败策略（统一原则：**不覆盖已有的好数据**）

| 场景 | 处理 | 是否写 Redis |
| :--- | :--- | :--- |
| 下发成功但 5s 内无回执 | Warn 日志（`echo`/`server_code`），等下一个 tick | 否 |
| 回执 `code != 200` 或 `status != SUCCESS` | Warn 日志（`code`/`status`/`api`） | 否 |
| `data` 为空 / `null`（RCON 未启用） | Warn 日志 | 否 |
| 回显文本解析失败 | Warn 日志（原始文本截断 512 字节） | 否 |
| 解析成功但 `len(players) != online` | Warn 日志，**仍写入**（人数是主指标，players 用实际解析结果） | 是 |
| Redis 写入失败 | Warn 日志，丢弃本次 | — |
| 查询时 Redis 故障 | 返回 error → 渲染「状态查询暂时不可用」 | — |

理由：一条异常样本（超时、RCON 临时故障、本地化文本）不能把上一个有效的玩家列表清空；宁可让旧值自然过期，也不主动写坏数据。

### 4.6 被否决的方案

| 方案 | 否决理由 |
| :--- | :--- |
| 全局 Hash `revolcast:server:status`（field = code） | 每个 field 无法单独设 TTL（`HEXPIRE` 需 Redis ≥ 7.4），掉线服务器会残留 field，必须在应用层按 `updated_at` 判过期；只有「一条指令看全部服务器」时才值得 |
| `meta` String + `players` ZSET 双键 | 多键多命令，为「谁何时进服」这类当前无需求的能力付复杂度；TTL 分键也难保持一致 |
| 状态落 PostgreSQL / MongoDB | 每分钟写库、查询要查表，直接违背本需求的核心目标，且数据本身是可丢弃的实时态 |
| 用 `player_join` / `player_quit` 事件做增量计数 | 进程重启、事件丢失会让计数永久漂移；`list uuids` 是服务端权威快照，可自愈 |

## 5. 协议层改动

### 5.1 下行 API：`send_rcon_command`

依据《鹊桥》文档「连接端 → 鹊桥 · 发送RCON命令」。

请求：

```json
{ "api": "send_rcon_command", "data": { "command": "list uuids" }, "echo": "rcon:<唯一ID>" }
```

回执（`post_type=response`）：

```json
{ "code": 200, "api": "send_rcon_command", "post_type": "response", "status": "SUCCESS",
  "message": "success",
  "data": "There are 3 of a max of 20 players online: Bot1 (51a4b33d-8b80-3bde-806f-de4086b03058), Bot2 (16beaa94-ff1b-37a7-8afb-c22dcb8c16d1), Bot3 (73f370b4-497b-347a-a6bb-50d07eb88947)",
  "echo": "rcon:<唯一ID>" }
```

注意：`send_rcon_command` 的 `data` 是**字符串**，而 `send_private_msg` 的 `data` 是**对象**。因此回执结构体的 `data` 必须用 `json.RawMessage` 承载，由调用方按 `api` 决定如何解码，不可统一声明为 `string` 或 `map`。

### 5.2 echo 关联机制（本次新增）

现状：`transport/ws_game_server.go` 收到 `post_type=response` 时**只打日志并丢弃**，注释亦写明「本期下行是尽力而为，不等待回执」。本次要拿到回显，必须补上关联映射。

```
GameServerClient
  rconMu    sync.Mutex
  rconWait  map[string]chan string   // echo -> 回执通道（buffered 1）
```

流程：

1. 采集协程生成 `echo = "rcon:" + protocol.NewCommandID()`（全局唯一）；
2. 注册 `rconWait[echo]` → `deliver(请求)` → `select` 等回执或超时（默认 5s）；
3. 收到 `post_type=response` 时先按 `echo` 查表：
   - **命中**：把 `data` 原样投进通道，随后从表中删除；**不投递业务队列**；
   - **未命中**（`send_private_msg` 等无等待方的下行）：保持现有行为，仅按 `code`/`status` 记日志。
4. 超时、连接关闭时删除表项并唤醒等待方（返回失败），避免 goroutine 与内存泄漏。

约束：

- **每连接同时只允许 1 个在途 RCON 请求**：由「同一个采集协程发完就等」天然保证，不需要额外的信号量。
- `map` 仍需按 echo 精确匹配（而不是「收到 response 就当状态」），否则将来新增其他 RCON 指令会串台。
- 回执消息体上限 `wsMaxMessageLen` = 512KB，玩家列表远小于此值，无需调整。

### 5.3 定时器

| 项 | 取值 |
| :--- | :--- |
| 触发点 | `GameServerClient.start()` 时启动 `runStatusPoller` 协程 |
| 首次执行 | 连接建立后**先等一个周期**（默认 60s）再拉第一次，见下方说明 |
| 周期 | 默认 60s，配置项 `ws.status_poll_interval_seconds` |
| 超时 | 默认 5s，配置项 `ws.status_poll_timeout_seconds` |
| 节奏 | 「发 → 等 ≤5s → 重置 timer 到下一周期」，避免 ticker 在超时时堆积 |
| 退出 | 连接关闭（`stop()`）时结束并 `DELETE` 状态键 |

> **首次延迟一个完整周期（实现期调整）**：服务器刚接入时往往还在初始化（鹊桥 / RCON 未必就绪），
> 立即拉取大概率拿到空回显，只会白打一次失败日志。因此首个 timer 初值取 `pollInterval` 而非 0。
> 代价是新连接的服务器在首分钟内查询返回「未找到」，属于有意取舍；首次延迟与采集周期共用同一配置项。

## 6. 回显解析

### 6.1 目标格式（英文原版）

```
There are <online> of a max of <max> players online: <昵称> (<uuid>), <昵称> (<uuid>), ...
```

空服务器（无冒号后内容，部分版本保留冒号）：

```
There are 0 of a max of 20 players online:
```

### 6.2 解析规则

1. 头部：`^There are (\d+) of a max of (\d+) players online:?` —— 不匹配则返回 error。
2. 尾部：按半角逗号 `,` 切分（每项 `trim` 后跳过空项），逐项匹配 `^(.+) \(([0-9a-fA-F]{8}-[0-9a-fA-F-]{27,36})\)$`；不匹配的项单独记 Warn 并跳过，不影响整体。
3. `online` 取头部数字（**不用** `len(players)`）；若 `len(players) != online`，记 Warn（回显被截断 / 昵称含异常字符），仍返回解析结果。

### 6.3 边界样例（须进单测）

| 输入 | 期望 |
| :--- | :--- |
| 文档原样 3 人示例 | `online=3, max=20, players=3` |
| `There are 0 of a max of 20 players online:` | `online=0, players=[]`，正常写入（渲染「没有玩家在线」） |
| 昵称含空格 `Notch Jr. (uuid)` | 昵称 `Notch Jr.`，uuid 正确 |
| 昵称含中文 `小明 (uuid)` | 正常解析 |
| 昵称含逗号 | 按逗号切分会切坏 → 该条跳过 + Warn，整体仍成功 |
| `RCON is not enabled` / 空串 | 返回 error，**不写 Redis** |
| 中文回显（zh_CN 服务端） | 头部不匹配 → error → 不写 Redis，旧值自然过期（见 §6.4） |

### 6.4 locale 风险（已知限制）

`list` 回显由服务端语言包生成。若服务器改为中文 locale，回显会变成「当前有 3 名玩家，最多 20 名玩家在线：…」，`§6.2` 的英文正则全部失效。

处理方式（D5 决策）：**不做中英双正则**，解析失败 → 记 Warn + 不写。表现是「状态查询会一直回未找到」，属于**可见的、可上报的**降级，而不是把错误数据写进缓存。将来若真有中文服接入，再在 `protocol.ParseListUUIDsEcho` 内部追加模式即可（解析函数与存储格式解耦，扩展不影响存量数据）。

### 6.5 并发 / 加密风险

`list uuids` 每分钟在服务端控制台产生一条 RCON 执行记录，属于可接受的运维噪音；若服务器开启了命令日志审计，需要注意频率。

## 7. 业务层

新增 `biz.GameStatusService`（平台无关，不依赖 WS 运行时）：

```go
// RecordListUUIDs 解析鹊桥回执并写入 Redis（采集侧调用）。
// 解析失败只记日志、不覆盖旧值；serverID 来自连接已鉴权身份，不接受外部传入。
func (s *GameStatusService) RecordListUUIDs(ctx context.Context, serverID int64, serverCode, rawEcho string)

// GetStatus 读取状态快照（查询侧调用）。
// 键不存在返回 (nil, nil) —— 「没有数据」是可预期的业务分支，不用 error 表达；
// Redis 故障返回 Wrap(ErrInternal, ...) ，由 transport 渲染为「暂时不可用」。
func (s *GameStatusService) GetStatus(ctx context.Context, serverCode string) (*repository.ServerStatusRecord, error)

// ClearStatus 断连时删除状态键（尽力而为，失败只记日志，TTL 兜底）。
func (s *GameStatusService) ClearStatus(ctx context.Context, serverCode string)
```

依赖注入：`StatusCache` 接口（`GetCache` / `SetCache` / `DelCache`），生产实现为 `*repository.RedisRepo` —— **复用现有三个方法，不新增仓储方法**，仅新增键构造函数 `repository.ServerStatusKey(code)` 与记录结构 `repository.ServerStatusRecord`。

> `GameStatusService` 不校验 `game_servers.status`：键存在的前提就是「该服务器持有有效 secret 且当前连着」，本身就是最强的一致性证明；再查表只会引入一次无谓的 DB 往返。

## 8. QQ 指令

### 8.1 识别

`transport/handler.go` 的 `parseCommand`（`strings.Fields`，大小写/空白不敏感）新增一个分支：

```go
case len(tokens) == 4 && tokens[1] == "server" && tokens[3] == "status":
    return commandServerStatus, tokens[2]
```

与 `bind` / `unbind` 同层（都是 4 个词），靠第 4 个词区分。帮助文案新增一行：

```
revolcast server <代号> status —— 查看该服务器当前在线人数
```

### 8.2 渲染

| 分支 | 文案 |
| :--- | :--- |
| 有玩家 | `当前服务器有 3 人：Bot1，Bot2，Bot3` |
| 0 人 | `当前服务器没有玩家在线。` |
| 超过 30 人 | `当前服务器有 42 人：A，B，……（仅显示前 30 人）` |
| 键不存在 | `未找到「survival」的服务器状态，该服务器可能尚未连接，请稍后再试或联系管理员。` |
| Redis 故障 | `状态查询暂时不可用，请稍后再试。` |

- 昵称用全角逗号 `，` 连接（与 QQ 文案风格一致，也与需求示例一致）。
- 最多展示 30 个昵称（QQ 单条消息长度有限，人多时折叠反而更难读）。
- 文案不暴露 Redis / 内部错误细节（细节只进日志）。

### 8.3 限流

**不加限流**：一次查询的成本是 1 次 `GET`，与 `revolcast server list`（同样不加）同量级。若后续出现刷屏，再补 `revolcast:ratelimit:qq:server_status:{qq_uin}`（5 分钟 / 30 次，fail-open），不影响本期实现。

## 9. 生命周期

| 事件 | 动作 |
| :--- | :--- |
| WS 连接建立（鉴权通过） | 启动采集协程，**等一个周期后**拉第一次（默认 60s，见 §5.3） |
| 采集成功 | `SET` 覆盖 + TTL 重置 |
| 采集失败 | 不写，等下一 tick |
| 连接注销（`readPump` 退出 / 被踢旧 / 优雅关闭） | 采集协程退出 → `DEL` 键（失败忽略） |
| 进程崩溃 | TTL 180s 兜底过期 |

**多实例部署**：目前 WS 连接索引在进程内，多实例时同一服务器可能被多个实例同时轮询，各自 `SET` 相同的值（写覆盖，无副作用）。若将来需要严格单点采集，应引入实例级 leader 选举或在连接层做粘性路由，本期不做。

## 15. 实施记录（已实现）

实现与本文档的差异如下（其余按 §11 落地）：

| 项 | 设计 | 实现 | 原因 |
| :--- | :--- | :--- | :--- |
| 采集结果的落地调用 | biz 内部记日志 | `RecordListUUIDs` 返回 `error`，由 transport 记 Warn | 本项目 biz 层不持有 logger（沿用 `GameEventService` 等既有约定），日志统一在 transport |
| 查询返回类型 | `*repository.ServerStatusRecord` | `*biz.ServerStatusView`（biz 自有视图） | transport 不直接依赖 repository，保持 biz 作为业务边界 |
| `ServeGameServerWS` 签名 | 注入 sink | `ServeGameServerWS(hub, auth, statusSink, opts, logger)` | sink 为 nil 时该连接不采集（便于单测） |
| 采集参数 | 独立配置节 | `ws.status_poll_interval_seconds`（默认 60）/ `ws.status_poll_timeout_seconds`（默认 5） | 复用既有 `ws` 配置节，避免新增顶层节 |
| `list uuids` 回执为空 | — | 视为采集失败（返回 error，不写快照） | RCON 未启用 / 命令未执行时 `data` 可能为 `null` 或空串 |
| 首次采集时机 | 连接建立后立即拉一次（原 §5.3） | **延迟一个 `pollInterval`（默认 60s）**，timer 初值取 `pollInterval` 而非 0 | 服务器刚接入时 RCON 常未就绪，立即拉只会白打一次失败日志；代价是首分钟内查询返回「未找到」（改动经用户确认，属临时调整） |
