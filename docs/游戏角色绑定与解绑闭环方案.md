# 游戏角色绑定与解绑闭环方案

> 状态：**已实现**（2026-10-23；落地差异见 §17）
> 关联文档：《Revolcast业务流程设计文档》§2.9（BIZ-009）、《Revolcast_数据库表设计文档_v1.1》§3.6 / §3.7 / §6.2、《鹊桥与服务端WS连接格式详解》「连接端 → 鹊桥 · 私聊消息」、《Revolcast_HTTP接口设计文档》§13、《Websocket消息结构设计文档》§4
> 关联代码：`backend/internal/transport/handler.go`、`ws_game_server.go`、`ws_hub.go`、`ws_push.go`、`backend/internal/biz/game_bind_service.go`、`backend/internal/repository/server_game_binding.go`

---

## 1. 目标

补齐「网站账号 ↔ 游戏角色」链路的最后一环：用户在 QQ 拿到绑定码后，能在游戏内完成绑定；绑定后也能在 QQ 解除。完成后整条链路闭环：

```
QQ 私聊 revocast server <code> bind  →  game_bind_codes(status=0)   [已实现 BIZ-009]
游戏内 /revolcast bind <code>        →  server_game_bindings(status=1) + 码置 1   [本次 BIZ-010]
QQ 私聊 revocast server <code> unbind →  server_game_bindings(status=0)           [本次 BIZ-011]
```

| 指令 | 触发位置 | 执行结果 | 业务编号 |
| --- | --- | --- | --- |
| `/revolcast bind <code>` | 游戏内（鹊桥 `player_command` 事件） | 消费绑定码并创建角色绑定，游戏内私聊回执 | **BIZ-010** |
| `revolcast server <code> unbind` | QQ 私聊 | 软解绑当前有效角色绑定，QQ 私聊回执 | **BIZ-011** |

## 2. 范围

**本期实现**

1. 鹊桥下行通道抽象：后端按 `server_id` 向已连接的游戏服务器下发鹊桥原生指令（`send_private_msg`），作为**所有游戏内通知的唯一出口**（绑定结果、解绑通知、后续的其它通知都复用它）。
2. `player_command` 事件新增命令分发（`revolcast bind <code>`），可继续扩展其它命令。
3. BIZ-010 赎回事务：原子消费 `game_bind_codes` + 写入 `server_game_bindings`。
4. BIZ-011 解绑：QQ 私聊指令 + 软解绑。
5. `player_command` 事件**不再对外可见**（不推 WS、HTTP 也查不到），只保留 MongoDB 审计。
6. 游戏内绑定限流（5 分钟 5 次，前置计数）。

**本期不做（明确边界）**

- 网站侧角色解绑 / 角色管理页：本次只做 QQ 指令入口。
- 隐身（`visibility=0`）过滤：见 §15 关注点 6。
- 绑定成功后额外通知 QQ：需要定位「哪个 adapter 连接代表该 QQ」，当前 adapter 为共享 token + 自报 `client_id`，无可靠映射，见 §15 关注点 5。
- 解绑限流：解绑为幂等、单行 UPDATE、低风险，默认不限流（见 §15 关注点 3）。
- adapter 改动：**零改动**。原因见 §4.2。
- `server_messages`（转发到 Web/QQ 的聊天消息）：与本次无关，不要复用。

## 3. 已确认决策（本轮评审确认）

| # | 决策项 | 结论 |
| --- | --- | --- |
| 1 | 绑定码是否脱敏 | **不脱敏**，但 `player_command` 事件**不再对外暴露**（不推 WS、HTTP 查询排除），码只存在于 MongoDB 审计日志与游戏服务器本地 |
| 2 | 游戏内绑定限流位置 | **前置**：解析出码后立即计数，命中即拒绝（拦住暴力猜码） |
| 3 | 命中的角色已被其他账号绑定 | **拒绝**并提示「该角色已被其他账号绑定」，不做顶号 |
| 4 | 游戏端 `player_command` 是否可靠上报 | **已确认**：`/revolcast` 命令会触发事件上报，直接实现 |

### 3.1 与既有约定的一致性

- 命令识别只在 backend（BIZ-001 / 008 / 009 的既定约束），**不新增 adapter 逻辑**。用户描述的「在 adapter 中新增命令」按项目约定落在 `transport/handler.go` 的 `parseCommand`。
- 可预期的业务分支（码无效 / 已绑定 / 角色被占 / 无绑定可解）用**结果对象**返回，`errorMeta` **零新增**，只有真失败（限流 / 账号禁用 / 服务器停用 / DB 异常）走 `error`。
- 所有 DB 写入失败必须 `Wrap(ErrInternal, cause, ctx)` 携带根因，日志输出完整链。

## 4. 命令协议

### 4.1 游戏内命令（BIZ-010 入口）

来源：`task.Type == event.game.player_command`（鹊桥 `player_command` 事件），`command` 字段**不含前导 `/`**（见鹊桥文档）。

```
/revolcast bind <code>            ← 用户在游戏里实际输入
```

解析规则（`transport/handler.go` 新增 `parseGameCommand`）：

1. 去掉可能残留的前导 `/`，按 `strings.Fields` 切词（空白不敏感）。
2. 首词处理：
   - `revolcast` → 命令词取第 2 个 token；
   - `revolcast:<sub>`（Forge 命名空间形式）→ 命令词取 `<sub>`，参数从第 2 个 token 起。
   - 其它 → **静默丢弃**（普通 `/tp`、`/gamemode` 等不打扰，也不写业务日志）。
3. `bind` 需要且仅需要 1 个参数：
   - 参数缺失 → 回「用法」提示（不静默，便于玩家自查）；
   - 参数多于 1 个 → 按用法错误处理。
4. 绑定码规范化：`TrimSpace` + `ToUpper`（用户可能输小写）；再做长度 8 + 字符集校验（`ABCDEFGHJKMNPQRSTUVWXYZ23456789`），非法直接按「码无效」处理，**不查库**。
5. 其它命令词 → 暂静默（后续在此 case 扩展）。

> 命令词与参数只影响「是否进入绑定流程」，玩家身份（`player.uuid` / `nickname`）与归属服务器（`server_id`）一律来自**已鉴权 WS 连接**与事件体，不接受玩家自报。

### 4.2 QQ 私聊命令（BIZ-011 入口）

在既有 `parseCommand` 词序表中新增一行：

| 词序列 | 结果 |
| --- | --- |
| `revolcast` `server` `<code>` `unbind` | 新增：`commandServerUnbind`（BIZ-011） |
| 其它（既有） | 不变 |

同时更新 `commandHelpText`，补上 `revolcast server <代号> unbind —— 解除该服务器的角色绑定`。

## 5. 鹊桥下行通道（本次的核心抽象）

### 5.1 为什么不经统一 Envelope

`/api/v1/game-servers/ws` 的对端是鹊桥 mod，只认鹊桥原生 JSON（上行是裸 JSON，下行同样）。统一 Envelope 只适用于 Adapter / Web 两个接入端。这条边界已在现有上行实现中确立（`parseGameServerEvent`），本次下行延续同一规则，并补进《Websocket消息结构设计文档》。

### 5.2 请求 DTO（`protocol/game_command.go` 新增）

```go
// 对应鹊桥文档「连接端 → 鹊桥 · 私聊消息」
type GamePrivateMessageRequest struct {
    API  string                   `json:"api"`  // 固定 "send_private_msg"
    Data GamePrivateMessageData   `json:"data"`
    Echo string                   `json:"echo"` // 唯一回执标识，供日志关联
}

type GamePrivateMessageData struct {
    UUID     string              `json:"uuid,omitempty"`     // 优先
    Nickname string              `json:"nickname,omitempty"` // uuid 为空时兜底
    Message  []GameTextComponent `json:"message"`            // Minecraft 文本组件数组
}

type GameTextComponent struct {
    Text  string `json:"text"`
    Color string `json:"color,omitempty"` // red / green / yellow / aqua / white / gray
}

const GameAPISendPrivateMsg = "send_private_msg"
```

发送时 `uuid` 与 `nickname` 至少一个非空（鹊桥文档要求）；两者都给时鹊桥优先 `uuid`。

### 5.3 发送函数（唯一出口）

`transport/game_notice.go`（新增）：

```go
// GameNotifier 是后端向游戏内玩家发送私聊通知的唯一入口。
// 后续绑定通知、解绑通知、系统公告都复用它，不要在别处直接拼鹊桥 JSON。
type GameNotifier struct {
    hub *Hub
    log *zap.Logger
}

func (n *GameNotifier) SendText(serverID int64, p protocol.QueqiaoPlayer, color, text string) bool
```

职责：

1. 组装 `GamePrivateMessageRequest`（`echo = protocol.NewCommandID()`）；
2. `hub.SendToGameServerByID(serverID, bytes)`；
3. 返回是否成功入队，**失败只记 Warn 日志**（不重试、不阻塞、不影响业务结论）。

`Hub` 需要新增按 `server_id` 查连接的索引（见 §10.3）。

### 5.4 下行回执处理

鹊桥通过同一 WS 返回：

```json
{ "code": 200, "api": "send_private_msg", "post_type": "response", "status": "SUCCESS", "echo": "..." }
```

`ws_game_server.go` 的 `parseGameServerEvent` 目前只认 `sub_type`，会把回执当「缺少 sub_type」打 Warn。改为：

| 条件 | 处理 |
| --- | --- |
| `post_type == "response"` | 回执：按 `echo` 记 Debug 日志（成功）/ Warn 日志（`code != 200` 或 `status != SUCCESS`），**不入业务队列** |
| `post_type` ∈ {`notice`, `message`} 且 `sub_type` 非空 | 事件（现有逻辑） |
| 其它 | Warn 丢弃 |

本期的通知是「尽力而为」：**不等待回执**。若将来需要确认送达，再引入 echo → 等待方映射（会引入状态管理，本期不做）。

### 5.5 失败语义

| 场景 | 行为 |
| --- | --- |
| 游戏服务器连接不在线 | 通知丢弃，记 Warn；业务结果不变（绑定已落库） |
| 发送队列满 | 同上 |
| 鹊桥回执非 200 | 记 Warn，不重试 |
| 玩家离线（解绑通知） | 同上，鹊桥返回失败只进日志 |

**结论：绑定/解绑的业务成败只由数据库事务决定，通知是附属效果。**

## 6. BIZ-010：游戏内绑定

### 6.1 主流程

| 步骤 | 处理 |
| --- | --- |
| 01 | **接收事件** — 鹊桥上报 `player_command`，transport 由 `sub_type` 派生 `event.game.player_command`，业务归属 `server_id` 来自已鉴权连接 |
| 02 | **落库审计** — `GameEventService.Ingest` 写入 `game_events`（**保留命令原文，不脱敏**，仅内部审计） |
| 03 | **命令分发** — `transport.handleGameCommand` 解析命令；非 `revolcast` 命令直接结束（静默） |
| 04 | **码格式校验** — 长度 8、字符集合法；不合法 → 直接回「绑定码无效」，不查库、不计数 |
| 05 | **限流（前置）** — Redis `revolcast:ratelimit:game:redeem:{server_id}:{player_uuid}`，5 分钟 5 次，`fail-open`；命中 → 私聊提示「操作过于频繁」并结束 |
| 06 | **赎回事务** — 单事务内完成 §6.2 的 1~7 步 |
| 07 | **结果渲染** — 按 `GameRoleBindOutcome` 选文案（§6.4） |
| 08 | **私聊回执** — `GameNotifier.SendText` 发给该玩家（`uuid` 优先） |
| 09 | **事件不推送** — `player_command` 不进 Web 事件流（§8） |

`Ingest` 与业务处理的顺序是刻意的：**先落库再处理业务**，保证即使绑定逻辑失败，玩家的命令审计也不丢。

### 6.2 赎回事务（`ServerGameBindingRepo.RedeemGameBindCode`）

单事务，`READ COMMITTED`（默认）：

```sql
-- 1) 锁定待使用码（行锁，防止并发重复消费）
SELECT id, user_id, qq_uin FROM game_bind_codes
 WHERE code = $1 AND server_id = $2 AND status = 0 AND expires_at > now()
   FOR UPDATE;

-- 1b) 未命中时做一次幂等重放判定：同码 + 同角色已绑定成功
SELECT c.id, b.id, b.user_id, b.game_name
  FROM game_bind_codes c
  JOIN server_game_bindings b ON b.bind_code_id = c.id AND b.status = 1
 WHERE c.code = $1 AND c.server_id = $2 AND c.status = 1 AND b.game_uuid = $3
 LIMIT 1;
--   命中 → outcome = already_bound（重复输入/消息重投，回「绑定成功」）
--   未命中 → outcome = code_invalid

-- 2) 服务器状态（停用则拒绝，避免给已下线的服务器建绑定）
SELECT status, code, name FROM game_servers WHERE id = $1;
--   status != 1 → outcome = server_unavailable

-- 3) 账号状态
SELECT status FROM users WHERE id = $user_id;
--   status != 1 → outcome = account_disabled

-- 4) 该账号在本服已有有效角色？
SELECT game_name FROM server_game_bindings
 WHERE server_id = $1 AND user_id = $2 AND status = 1 LIMIT 1;
--   命中 → outcome = account_bound（回显已有角色名）

-- 5) 角色是否已被其他账号占用（UUID 或角色名，名字按大小写不敏感）
SELECT user_id, game_name FROM server_game_bindings
 WHERE server_id = $1 AND status = 1
   AND (game_uuid = $uuid OR lower(game_name) = lower($game_name))
 LIMIT 1;
--   命中且 user_id <> $user_id → outcome = role_taken
--   命中且 user_id = $user_id → 理论上前一步已拦截，按 account_bound 处理

-- 6) 消费绑定码，回填角色快照
UPDATE game_bind_codes
   SET status = 1, used_at = now(), game_name = $3, game_uuid = $4
 WHERE id = $codeID;

-- 7) 写入角色绑定（visibility 默认 1 公开，status=1）
INSERT INTO server_game_bindings
  (server_id, user_id, game_name, game_uuid, bind_code_id, visibility, status, bound_at, created_at, updated_at)
VALUES ($1, $2, $3, $4, $5, 1, 1, now(), now(), now());
```

**并发与冲突**

- 两个并发请求消费同一码：`FOR UPDATE` 串行化，后到者在 `status=0` 谓词上得到 0 行 → 走 1b 幂等判定或 `code_invalid`。
- INSERT 撞唯一约束（此时整个事务回滚，**码状态恢复为 0**，用户可换角色重试同一码）：

| 约束 | 映射 |
| --- | --- |
| `ux_server_game_bindings_active_user` | `account_bound` |
| `ux_server_game_bindings_active_uuid` | `role_taken` |
| `ux_server_game_bindings_active_name` | `role_taken` |

**角色身份校验**

- `player.uuid` 为空或不是合法 UUID（`8-4-4-4-12` 十六进制）→ `code_invalid` 之外的独立结果 `player_invalid`，文案提示「无法识别你的游戏角色，请联系服务器管理员」。
- `player.uuid` 是 `**server_game_bindings.game_uuid`（PostgreSQL `uuid` 类型）**的唯一来源；`game_name` 取 `player.nickname`，均为**服务器上报的不可信数据但由已鉴权服务器提供**，接受其为准。

**为什么不做「先查后写」的两段式校验**：所有判定都必须在同一事务内基于同一快照完成，否则「校验通过 → 写入」之间角色被他人抢先绑定，唯一索引会兜底但错误文案会失真。事务内预检 + 唯一索引兜底是双保险。

### 6.3 结果分支（biz 层 `GameRoleBindOutcome`）

| Kind | 触发条件 | 是否 `error` |
| --- | --- | --- |
| `bound` | 新绑定成功 | 否 |
| `already_bound` | 同码同角色重复提交（幂等） | 否 |
| `code_invalid` | 码不存在 / 已使用（不同角色）/ 已过期 / 跨服 / 格式非法 | 否 |
| `account_bound` | 该账号在本服已有有效角色（携带已有角色名） | 否 |
| `role_taken` | 角色（UUID 或名字）已被其他账号占用 | 否 |
| `server_unavailable` | 绑定码所属服务器已停用 | 否 |
| `player_invalid` | 玩家 UUID 缺失或格式非法 | 否 |
| — | 限流 | `ErrRateLimited`（复用） |
| — | 账号被禁用 | `ErrAccountDisabled`（复用） |
| — | DB 失败 | `ErrInternal` + 根因 |

### 6.4 游戏内文案（`GameTextComponent`，鹊桥自动加 `[鹊桥]` 前缀）

**A. 绑定成功 / 幂等成功**（green）
```
✔ 绑定成功
角色：Steve
服务器：元素觉醒（element）
如需解绑，请在 QQ 私聊发送：revolcast server element unbind
```

**B. 绑定码无效**（red）
```
✘ 绑定码无效或已过期。
请在 QQ 中私聊发送「revolcast server element bind」重新获取绑定码。
```

**C. 账号已在本服绑定角色**（yellow）
```
你在本服务器已绑定角色：Steve
一个账号在同一服务器只能绑定一个角色。如需更换，请先在 QQ 私聊解绑。
```

**D. 角色已被其他账号占用**（red）
```
✘ 该角色已被其他 Revolcast 账号绑定。
请先在原账号解绑，或联系服务器管理员处理。
```

**E. 服务器已停用**（red）
```
✘ 该服务器当前不可用，绑定未生效。
```

**F. 无法识别角色**（red）
```
✘ 无法识别你的游戏角色，请联系服务器管理员。
```

**G. 限流**（yellow）—— 复用 `ErrRateLimited.WSMessage`，但改成游戏内口气：
```
✘ 操作过于频繁，请 5 分钟后再试。
```

**H. 用法错误**（yellow）
```
用法：/revolcast bind <8 位绑定码>
绑定码请在 QQ 私聊发送「revolcast server <代号> bind」获取。
```

> 文案在 transport 层渲染（与 QQ 文案同层），biz 只返回结论，不拼文案。

### 6.5 边界与异常

| 场景 | 处理 |
| --- | --- |
| 玩家在 A 服输入 B 服的码 | 按 `(code, server_id)` 查，A 服查不到 → `code_invalid`（不泄露该码是否存在于 B 服） |
| 玩家输入过期码 | `code_invalid`；行仍为 `status=0`，由下次发码时的 `reclaimExpiredPending` 回收槽位 |
| 玩家重复输入同一码（已成功） | 幂等 → `already_bound`，回「绑定成功」，避免重复操作困惑 |
| 同一码被两个玩家同时输入 | 事务行锁；后者 `code_invalid` |
| 玩家绑定成功后立刻解绑再绑 | 解绑后旧行 `status=0`，可重新发码绑定（新行） |
| 绑定码泄露给他人 | **码即持有者凭证**：谁输入就绑谁的角色到码所属账号。风险已知，靠 10 分钟 TTL + 限流 + 不对外展示缓解 |
| 事件重复投递（MQ 重投） | 幂等分支覆盖 |
| 私聊回执失败 | 绑定已落库，仅日志；玩家可重输同一码得到幂等结果 |

## 7. BIZ-011：QQ 解除角色绑定

### 7.1 主流程

| 步骤 | 处理 |
| --- | --- |
| 01 | **识别命令** — `revolcast server <code> unbind`，`code` 转小写 |
| 02 | **服务器校验** — `ResolveServer` 直查库（**不校验 `status`**，停用服务器也允许解绑），格式非法 / 不存在统一「未找到代号为「xxx」的服务器」 |
| 03 | **QQ → 账号** — `qq_bindings(status=1)` 取 `user_id`；无 → `GameRoleUnbindQQNotBound`（引导 `revolcast user bind`） |
| 04 | **软解绑** — `UPDATE ... WHERE server_id AND user_id AND status=1 RETURNING game_name` |
| 05 | **QQ 回执** — 成功 / 无绑定分别文案 |
| 06 | **游戏内通知（尽力而为）** — 若该服务器当前有连接，向该角色发私聊「绑定已解除」；离线/失败只记日志 |

### 7.2 SQL

```sql
UPDATE server_game_bindings
   SET status = 0, unbound_at = now(), updated_at = now()
 WHERE server_id = $1 AND user_id = $2 AND status = 1
 RETURNING id, game_name, game_uuid;
```

- 0 行 → `not_bound`。
- 单条 UPDATE 原子，无需显式事务；并发重复解绑只有一个命中。
- **不删除历史行**（`status=0` 保留审计），符合数据库文档 §3.7「保留历史」。
- 不联动修改 `game_bind_codes`（已使用的码保持 `status=1` 作为审计）。
- **为什么用 `ResolveServer` 而不是 `ResolveSubscribableServer`**：后者会拒绝已停用服务器，而解绑是「对已存在关系生效」的操作——若因服务器停用而无法解绑，用户的历史绑定会被永久锁死。发码 / 订阅事件这类「此刻能否使用该服务器」的判定仍必须走 `ResolveSubscribableServer`。

### 7.3 QQ 文案

**A. 解绑成功**
```
已解除在服务器「元素觉醒」的角色绑定：Steve
如需重新绑定，可在该服务器内重新获取绑定码后输入。
```

**B. 无有效绑定**
```
你在服务器「元素觉醒」没有已绑定的角色，无需解绑。
```

**C. QQ 未绑定账号** —— 复用 BIZ-009 的文案（引导 `revolcast user bind`）。

**D. 服务器不存在 / 停用** —— 复用 BIZ-009 的统一文案 + `server list` 指引。

### 7.4 游戏内解绑通知（尽力而为）

green：
```
你的 Revolcast 账号与该角色的绑定已解除。
```
玩家离线（鹊桥找不到目标）→ 只记 Debug/Warn 日志，不影响 QQ 回执。

## 8. 事件可见性调整：`player_command` 不再对外

### 8.1 规则

| 出口 | 变更 |
| --- | --- |
| MongoDB `game_events` | **不变**：仍写入，保留命令原文（审计用） |

2. `biz/game_event_query.go` 的 `Query` 固定传 `repository.GameEventQuery.ExcludeEventTypes = []string{"player_command"}`；`GameEventRepo.QueryGameEvents` 的 filter 追加 `event_type: {$nin: [...]}`。
3. `ingest` 与游标逻辑不变（事件仍持久化，只是不对外）。

> `agent.md` 的 §4 协议约定不涉及此处；这是数据可见性策略，不是消息类型变更。

### 8.3 文档同步

- 《Revolcast_HTTP接口设计文档》§13：注明「`player_command` 属于内部审计事件，不出现在事件查询结果中」。
- 《Websocket消息结构设计文档》「推送消息：`event.game.<sub_type>`」：注明推送仅覆盖 `player_join` / `player_quit` / `player_chat`。

## 9. 限流

| 项 | 值 |
| --- | --- |
| 键 | `revolcast:ratelimit:game:redeem:{server_id}:{player_uuid}` |
| 窗口 / 上限 | 5 分钟 / 5 次 |
| 位置 | **码格式校验之后、一切 DB 查询之前**（前置计数） |
| 失败策略 | Redis 故障 `fail-open`（放行 + 记日志） |
| 超限反馈 | 游戏内私聊提示（§6.4 G） |

**为什么与 BIZ-009 的「限流后置」相反**：BIZ-009 是**发码**，只读幂等答案（已绑定/未绑 QQ）不该被限流挡住；BIZ-010 是**猜码**，每次错误尝试都必须计数，否则 8 位码可被枚举。

**为什么维度带 `server_id`**：不同服务器独立计数，避免一个服务器的刷尝试拖累另一个；玩家 UUID 在正版服稳定，离线服按名字生成也足以限制单角色。

配置化：`biz.GameBindConfig` 新增 `RedeemWindow` / `RedeemMax`（默认 5min / 5），由 `cmd/server/main.go` 传零值走默认。

## 15. 待确认 / 评审关注点

| # | 关注点 | 本方案默认取舍 |
| --- | --- | --- |
| 1 | `player_command` 是否彻底对外不可见 | **是**：WS 不推、HTTP 不返回，仅 MongoDB 内部审计。若希望前端仍能看到（只挡绑定码），需改为「脱敏后可见」，实现改为在 `Ingest` 时写入脱敏值 |
| 2 | 解绑后是否在游戏内通知该角色 | **做**，尽力而为（离线/失败只记日志） |
| 3 | 解绑是否也要限流 | **不加**：幂等、单行 UPDATE，且需要 QQ 已绑定账号才能触发 |
| 4 | 绑定成功后是否通知 QQ | **不做**：当前无法可靠定位代表该 QQ 的 adapter 连接（共享 token + 自报 client_id），需另开 adapter 身份方案 |
| 5 | 一个账号在同一服务器只能有一个角色 | **保持**（数据库唯一索引决定）；更换角色需先 unbind 再重新发码 |
| 6 | 隐身（`visibility=0`）是否随本次落地 | **不做**：`visibility` 目前无设置入口，恒为 1；逐事件查库的成本不划算，等隐身设置功能落地时以缓存方式实现（`ws_push.go` 的 `TODO(visibility)` 保留） |
| 7 | 绑定码「持有者凭证」语义 | 码泄露风险由 10 分钟 TTL + 不对外展示 + 限流缓解；如需更强保证，可要求「申请绑定码的 QQ」与「游戏内角色」二次确认（需游戏内 QQ 验证，超出本期） |
| 8 | 游戏内命令是否需要 mod 侧注册 `/revolcast` 空命令 | **已确认可收到事件**，无需 mod 改动；若联调发现未上报，需 mod 注册空命令（不影响本方案） |
