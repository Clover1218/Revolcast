# Revolcast 数据库表设计文档

**版本：** 1.1  
**整理日期：** 2026-10-20  
**适用范围：** Revolcast MVP 数据持久化设计  
**数据库：** PostgreSQL（账号、绑定、权限、服务器配置）、MongoDB（聊天消息历史）、Redis（缓存、在线状态、限流与短期状态）

---

## 1. 设计目标与边界

Revolcast 以网站作为主要消息客户端，QQ 机器人主要承担 QQ 绑定、游戏角色绑定流程辅助、查询与可选的私聊订阅通知。QQ 群不自动接收游戏聊天洪流；游戏内也不转发 QQ 群消息。

### 1.1 核心规则

1. 一个网站账号对应一个全局 QQ 绑定；一个 QQ 号同一时刻最多绑定一个网站账号。
2. 一个账号可以绑定多个 Minecraft 服务器中的游戏角色；每个服务器内，一个账号最多有一个有效角色名，一个游戏名同一时刻最多归属一个账号。
3. 绑定码有有效期，只能成功消费一次。消费绑定码与创建绑定关系必须在同一个数据库事务内完成。
4. 未注册或未绑定 QQ / 游戏角色的用户仍可作为网站游客浏览，但游客只能看到公开玩家的消息，不能以玩家身份发言。
5. 玩家在每个服务器的角色级设置中选择“公开”或“隐身”。该设置存放在 `server_game_bindings`，不是网站账号的全局设置。
6. 公开角色的消息可出现在网站公开消息流；隐身角色的消息不向网站公开访客展示。可见性规则必须在后端查询、搜索、WebSocket 推送以及 QQ 私聊订阅推送处统一执行，不能只靠前端隐藏。
7. 不自动将游戏消息转发到 QQ 群，也不把 QQ 群消息转发进游戏。未来如需群内讨论，可由用户主动分享网站消息链接。
8. PostgreSQL 保存账号、绑定、权限和配置等结构化权威数据；MongoDB 保存聊天消息历史；Redis 只存缓存、限流、在线/短期状态等可重建数据。

### 1.2 数据存储分工

| 存储         | 负责内容                               | 不负责内容              |
| ---------- | ---------------------------------- | ------------------ |
| PostgreSQL | 用户、QQ 绑定、绑定码、游戏服务器、群配置、游戏角色绑定、订阅配置 | 大规模聊天正文历史、瞬时在线状态   |
| MongoDB    | 游戏/网站消息历史、消息元数据、消息游标所需字段           | 用户/绑定关系的权威数据       |
| Redis      | 在线心跳缓存、短期状态、限流计数、短期幂等键/nonce（按需）   | 唯一权威绑定关系、不可丢失的消息历史 |

## 2. PostgreSQL 规范

### 2.1 通用约定

- 主键使用 `BIGINT GENERATED BY DEFAULT AS IDENTITY`（旧式 `BIGSERIAL` 也可，但全项目应统一）。
- 时间使用 `TIMESTAMPTZ`，数据库连接统一使用 UTC；客户端负责本地化展示。
- 所有业务状态字段使用 `SMALLINT` 并加 `CHECK`，或在后续迁移中改用 PostgreSQL enum；MVP 建议 `SMALLINT + CHECK`，便于迁移。
- `updated_at DEFAULT now()` 只会在插入时赋值，不会自动随更新变化；由应用层统一更新，或创建触发器。
- 所有 FK 都应明确 `NOT NULL` / `NULL` 语义及删除策略。
- 部分唯一索引用于保证“同一时刻只有一条有效绑定”，解绑记录保留用于审计。
- `code` 使用 `VARCHAR(8)`，不使用固定宽度 `CHAR(8)`；生成时排除易混淆字符 `0/O/1/I/L`。
- 任何绑定码均应使用密码学安全随机数生成器。数据库不应把绑定码当成长期凭据；短有效期和一次性消费是必要条件。

### 2.2 表总览

| 表                              | 用途                         |
| ------------------------------ | -------------------------- |
| `users`                        | 网站账号                       |
| `qq_bindings`                  | 网站账号与 QQ 号的全局绑定历史          |
| `qq_bind_codes`                | QQ 绑定的一次性验证码               |
| `game_servers`                 | Minecraft 服务器注册与 API 鉴权配置  |
| `server_groups`                | QQ 群与游戏服务器的配置关联            |
| `game_bind_codes`              | 网站账号申请、由游戏内命令完成验证的一次性绑定码   |
| `server_game_bindings`         | 网站账号在单个游戏服务器中的角色绑定与公开/隐身设置 |
| `server_message_subscriptions` | 用户对服务器消息的 QQ 私聊订阅设置        |
| `web_sessions`                 | 网站登录会话（登录接口基座）                 |

## 3. PostgreSQL 表结构

### 3.1 `users` — 网站账号

| 字段              | 类型             | 约束 / 默认值                                      | 说明                                                     |
| --------------- | -------------- | --------------------------------------------- | ------------------------------------------------------ |
| `id`            | `BIGINT`       | PK, identity                                  | 账号 ID                                                  |
| `username`      | `VARCHAR(64)`  | NOT NULL                                      | 用户名；应用层统一规范化为小写后存储                                     |
| `password_hash` | `VARCHAR(255)` | NOT NULL                                      | 密码哈希；使用 bcrypt 则采用cost=12 |
| `email`         | `VARCHAR(255)` | NULL                                          | 可选邮箱                                                   |
| `status`        | `SMALLINT`     | NOT NULL DEFAULT 1, CHECK (`status IN (0,1)`) | 1=启用，0=禁用                                              |
| `created_at`    | `TIMESTAMPTZ`  | NOT NULL DEFAULT `now()`                      | 创建时间                                                   |
| `updated_at`    | `TIMESTAMPTZ`  | NOT NULL DEFAULT `now()`                      | 更新时间，由应用或触发器维护                                         |

**索引与约束**

- `PRIMARY KEY (id)`
- `UNIQUE (lower(username))`，使用唯一表达式索引，避免大小写用户名重复。
- 可按需求增加 `UNIQUE (lower(email)) WHERE email IS NOT NULL`；只有当产品规定邮箱全局唯一时才启用。

**规则**

- 禁用账号不能登录或发起新的绑定流程；是否允许只读访问由应用策略决定。
- 不在此表存 QQ 号或游戏名；这些身份属于独立绑定关系。

### 3.2 `qq_bindings` — QQ 全局绑定关系

| 字段           | 类型            | 约束 / 默认值                                      | 说明                                     |
| ------------ | ------------- | --------------------------------------------- | -------------------------------------- |
| `id`         | `BIGINT`      | PK, identity                                  | 记录 ID                                  |
| `user_id`    | `BIGINT`      | NOT NULL FK → `users.id`                      | 网站账号                                   |
| `qq_uin`     | `BIGINT`      | NOT NULL                                      | QQ UIN；按数字存储，不保留前导零                    |
| `bot_id`     | `VARCHAR(64)` | NOT NULL                                      | 完成绑定的稳定机器人/Adapter 逻辑 ID，不应使用易变化的连接 ID |
| `status`     | `SMALLINT`    | NOT NULL DEFAULT 1, CHECK (`status IN (0,1)`) | 1=有效，0=已解绑                             |
| `bound_at`   | `TIMESTAMPTZ` | NOT NULL DEFAULT `now()`                      | 绑定时间                                   |
| `unbound_at` | `TIMESTAMPTZ` | NULL                                          | 解绑时间                                   |
| `created_at` | `TIMESTAMPTZ` | NOT NULL DEFAULT `now()`                      | 创建时间                                   |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL DEFAULT `now()`                      | 更新时间                                   |

**索引与约束**

- `FOREIGN KEY (user_id) REFERENCES users(id)`
- `UNIQUE (qq_uin) WHERE status = 1`：同一 QQ 同时只能绑定一个账号。
- `UNIQUE (user_id) WHERE status = 1`：一个账号同时只能绑定一个 QQ。
- `INDEX (bot_id)`。

**规则**

- 解绑时更新当前行状态并设置 `unbound_at`，保留历史记录。
- `bot_id` 是来源/审计信息，不参与 QQ 的唯一性约束。
- 若不同部署环境中的 `bot_id` 不全局唯一，应将实例维度纳入该字段或另建 `bot_instances` 表。

### 3.3 `qq_bind_codes` — QQ 绑定码

| 字段                | 类型            | 约束 / 默认值                                          | 说明                      |
| ----------------- | ------------- | ------------------------------------------------- | ----------------------- |
| `id`              | `BIGINT`      | PK, identity                                      | 记录 ID                   |
| `code`            | `VARCHAR(8)`  | NOT NULL UNIQUE, CHECK 长度为 8                      | 一次性绑定码                  |
| `bot_id`          | `VARCHAR(64)` | NOT NULL                                          | 发码的机器人/Adapter ID       |
| `qq_uin`          | `BIGINT`      | NOT NULL                                          | 申请绑定的 QQ 号              |
| `trace_id`        | `VARCHAR(64)` | NULL                                              | 跨组件追踪 ID                |
| `status`          | `SMALLINT`    | NOT NULL DEFAULT 0, CHECK (`status IN (0,1,2,3)`) | 0=待使用，1=已使用，2=已过期，3=已取消 |
| `expires_at`      | `TIMESTAMPTZ` | NOT NULL                                          | 到期时间，建议创建后 5 分钟         |
| `used_by_user_id` | `BIGINT`      | NULL FK → `users.id`                              | 成功兑换该码的账号               |
| `used_at`         | `TIMESTAMPTZ` | NULL                                              | 兑换时间                    |
| `created_at`      | `TIMESTAMPTZ` | NOT NULL DEFAULT `now()`                          | 创建时间                    |

**索引与约束**

- `UNIQUE (code)`。
- `UNIQUE (qq_uin) WHERE status = 0`：同一 QQ 同时仅允许一条待使用绑定码，支撑生成阶段幂等取/建与并发安全；并发插入冲突时由业务回退到查询现有码。
- `INDEX (bot_id, qq_uin, expires_at) WHERE status = 0`。
- `CHECK (char_length(code) = 8)`；应用层限制字符集为 `A-Z0-9` 并排除 `0/O/1/I/L`。
- `FOREIGN KEY (used_by_user_id) REFERENCES users(id)`。

**消费规则**

- 兑换时必须通过单条条件更新原子消费，例如：`UPDATE ... SET status = 1, used_by_user_id = $user_id, used_at = now() WHERE code = $code AND status = 0 AND expires_at > now() RETURNING ...`。
- 若更新返回 0 行，则该码无效、过期或已被使用。
- 绑定记录创建与绑定码消费必须在同一个事务内完成。
- `expires_at` 是权威过期判断；后台任务更新 `status=2` 仅用于清理/展示，不可依赖定时任务保证安全。
- 生成阶段应保证同一 `qq_uin` 同时最多一条待使用码（见上方部分唯一索引 `UNIQUE (qq_uin) WHERE status = 0`）。并发申请时若插入因唯一约束冲突失败，应回退为查询并返回现有待使用码，实现幂等取/建。
- **生成前必须回收「已过期仍待使用」的旧码**：部分唯一索引的谓词只能是 `status = 0`（`now()` 不是 immutable 函数，不能出现在索引谓词中），因此 `expires_at <= now()` 但 `status` 仍为 0 的行会持续占用该 `qq_uin` 的唯一槽位。若直接插入新码，会一直撞 `ux_qq_bind_codes_pending_qq`；而回退查询（带 `expires_at > now()`）又查不到任何码，最终表现为「生成绑定码失败」。正确做法：插入前先执行 `UPDATE qq_bind_codes SET status = 2 WHERE qq_uin = $1 AND status = 0 AND expires_at <= now()`，把过期槽位释放出来再生成新码（`status = 2` 仅用于清理/展示，过期码本就不可兑换，不影响安全性）。

### 3.4 `game_servers` — 游戏服务器

| 字段                | 类型             | 约束 / 默认值                                      | 说明                                     |
| ----------------- | -------------- | --------------------------------------------- | -------------------------------------- |
| `id`              | `BIGINT`       | PK, identity                                  | 服务器 ID                                 |
| `code`            | `VARCHAR(64)`  | NOT NULL UNIQUE                               | 服务器短标识，建议只允许小写字母、数字、连字符                |
| `name`            | `VARCHAR(128)` | NOT NULL                                      | 展示名称                                   |
| `description`     | `TEXT`         | NULL                                          | 描述                                     |
| `api_secret_hash` | `VARCHAR(255)` | NOT NULL                                      | API Secret 的哈希值；原始 Secret 仅在创建/轮换时展示一次 |
| `status`          | `SMALLINT`     | NOT NULL DEFAULT 1, CHECK (`status IN (0,1)`) | 1=启用，0=停用                              |
| `created_at`      | `TIMESTAMPTZ`  | NOT NULL DEFAULT `now()`                      | 创建时间                                   |
| `updated_at`      | `TIMESTAMPTZ`  | NOT NULL DEFAULT `now()`                      | 更新时间                                   |

**索引与约束**

- `PRIMARY KEY (id)`。
- `UNIQUE (code)`。
- `CHECK (code ~ '^[a-z0-9-]+$')`。

**规则**

- `code` 用于 API 路径、指令参数和配置，不应依赖可变的 `name`。
- 若 Secret 仅用于校验，可保存安全哈希；若使用 HMAC 验签且必须用密钥计算签名，则需要可安全取回的密钥管理方案，不能直接用不可逆哈希替代 HMAC 密钥。
- 生产环境建议使用请求时间戳 + nonce + HMAC 签名，防止伪造和重放；密钥支持轮换与吊销。
- 在线人数、MOTD、心跳等动态状态不放在本表作为权威数据。

### 3.5 `server_groups` — QQ 群与服务器配置关联

| 字段           | 类型            | 约束 / 默认值                                      | 说明                   |
| ------------ | ------------- | --------------------------------------------- | -------------------- |
| `id`         | `BIGINT`      | PK, identity                                  | 记录 ID                |
| `server_id`  | `BIGINT`      | NOT NULL FK → `game_servers.id`               | 目标游戏服务器              |
| `bot_id`     | `VARCHAR(64)` | NOT NULL                                      | QQ 机器人/Adapter 逻辑 ID |
| `group_id`   | `BIGINT`      | NOT NULL                                      | QQ 群号                |
| `status`     | `SMALLINT`    | NOT NULL DEFAULT 1, CHECK (`status IN (0,1)`) | 1=启用，0=停用            |
| `created_at` | `TIMESTAMPTZ` | NOT NULL DEFAULT `now()`                      | 创建时间                 |

**索引与约束**

- `FOREIGN KEY (server_id) REFERENCES game_servers(id)`。
- `UNIQUE (server_id, bot_id, group_id) WHERE status = 1`。
- `INDEX (bot_id, group_id) WHERE status = 1`，供群消息/指令路由快速查找。
- `INDEX (server_id)`。

**规则**

- 同一个 QQ 群可以关联多个游戏服务器；同一服务器也可以关联多个群。
- 此表仅表示配置关联，不代表自动广播游戏聊天到 QQ 群。
- 若将来彻底移除群内查询/指令或其他群上下文功能，且群号不再参与任何业务，再考虑删除此表。

### 3.6 `game_bind_codes` — 游戏角色绑定码

| 字段           | 类型            | 约束 / 默认值                                          | 说明                                         |
| ------------ | ------------- | ------------------------------------------------- | ------------------------------------------ |
| `id`         | `BIGINT`      | PK, identity                                      | 记录 ID                                      |
| `code`       | `VARCHAR(8)`  | NOT NULL UNIQUE, CHECK 长度为 8                      | 一次性绑定码                                     |
| `server_id`  | `BIGINT`      | NOT NULL FK → `game_servers.id`                   | 目标服务器                                      |
| `user_id`    | `BIGINT`      | NOT NULL FK → `users.id`                          | 申请绑定的账号                                    |
| `qq_uin`     | `BIGINT`      | NULL                                              | 申请时 QQ UIN 快照，仅用于审计；不是权限依据                 |
| `trace_id`   | `VARCHAR(64)` | NULL                                              | 跨组件追踪 ID                                   |
| `status`     | `SMALLINT`    | NOT NULL DEFAULT 0, CHECK (`status IN (0,1,2,3)`) | 0=待使用，1=已使用，2=已过期，3=已取消                    |
| `game_name`  | `VARCHAR(64)` | NULL                                              | 验证成功后回填的游戏名快照                              |
| `game_uuid`  | `UUID`        | NULL                                              | 验证成功后回填的游戏内 UUID 快照；由目标 Minecraft 服务端验证后提供 |
| `expires_at` | `TIMESTAMPTZ` | NOT NULL                                          | 到期时间，建议创建后 10 分钟                           |
| `used_at`    | `TIMESTAMPTZ` | NULL                                              | 游戏内成功兑换时间                                  |
| `created_at` | `TIMESTAMPTZ` | NOT NULL DEFAULT `now()`                          | 创建时间                                       |

**索引与约束**

- `UNIQUE (code)`。
- `UNIQUE (server_id, user_id) WHERE status = 0`（`ux_game_bind_codes_pending_user`）：同一账号在同一服务器同时**最多一条待使用码**，用于并发下的幂等取/建与过期槽位回收。
- `FOREIGN KEY (server_id) REFERENCES game_servers(id)`。
- `FOREIGN KEY (user_id) REFERENCES users(id)`。
- `CHECK (char_length(code) = 8)`；字符集约束由生成器保证。

**规则**

- 绑定码绑定到指定服务器和指定账号；不可跨服务器兑换。
- 只有游戏服务器端实际验证到的游戏玩家名和 UUID 才可写入 `game_name`、`game_uuid`，不能信任网站客户端提交的名字或 UUID。
- `qq_uin` 为审计快照，可为空；账号权限仍以 `user_id` 和 `qq_bindings` 的有效关系为准。
- `game_name` 与 `game_uuid` 是本次绑定验证结果的快照；其中 `game_uuid` 使用 PostgreSQL 原生 `UUID` 类型。它们在绑定码成功消费时回填。
- 消费绑定码、校验当前账号/服务器状态、写入绑定关系必须在同一个事务内完成（跨服务场景采用明确的后端 API 流程和幂等处理）。

### 3.7 `server_game_bindings` — 服务器角色绑定与可见性

| 字段             | 类型            | 约束 / 默认值                                          | 说明                          |
| -------------- | ------------- | ------------------------------------------------- | --------------------------- |
| `id`           | `BIGINT`      | PK, identity                                      | 绑定记录 ID                     |
| `server_id`    | `BIGINT`      | NOT NULL FK → `game_servers.id`                   | 游戏服务器                       |
| `user_id`      | `BIGINT`      | NOT NULL FK → `users.id`                          | 网站账号                        |
| `game_name`    | `VARCHAR(64)` | NOT NULL                                          | 经游戏内验证的角色名；用于展示，不作为主要身份凭据   |
| `game_uuid`    | `UUID`        | NOT NULL                                          | 经可信游戏服务端验证的角色 UUID；用于识别绑定角色 |
| `bind_code_id` | `BIGINT`      | NULL FK → `game_bind_codes.id` ON DELETE SET NULL | 来源绑定码                       |
| `visibility`   | `SMALLINT`    | NOT NULL DEFAULT 1, CHECK (`visibility IN (0,1)`) | 1=公开，0=隐身；每个账号在每个服务器独立设置    |
| `status`       | `SMALLINT`    | NOT NULL DEFAULT 1, CHECK (`status IN (0,1)`)     | 1=有效，0=已解绑                  |
| `bound_at`     | `TIMESTAMPTZ` | NOT NULL DEFAULT `now()`                          | 绑定时间                        |
| `unbound_at`   | `TIMESTAMPTZ` | NULL                                              | 解绑时间                        |
| `created_at`   | `TIMESTAMPTZ` | NOT NULL DEFAULT `now()`                          | 创建时间                        |
| `updated_at`   | `TIMESTAMPTZ` | NOT NULL DEFAULT `now()`                          | 更新时间                        |

**索引与约束**

- `FOREIGN KEY (server_id) REFERENCES game_servers(id)`。
- `FOREIGN KEY (user_id) REFERENCES users(id)`。
- `FOREIGN KEY (bind_code_id) REFERENCES game_bind_codes(id) ON DELETE SET NULL`。
- `UNIQUE (server_id, user_id) WHERE status = 1`：一个账号在一个服务器最多有一个有效角色绑定。
- `UNIQUE (server_id, game_uuid) WHERE status = 1`：同一服务器内一个 UUID 最多对应一个有效账号。
- `UNIQUE (server_id, lower(game_name)) WHERE status = 1`：同一服务器内角色名按大小写不敏感规则最多对应一个有效账号；若目标服务端的名称规则不同，应相应调整。
- `INDEX (server_id) WHERE status = 1`。
- `game_uuid` 是角色身份的主要标识，`game_name` 是展示名称。名字可能变化，消息历史应保存发送时的名字快照。
- UUID 的稳定性取决于服务器身份体系：正版验证通常提供稳定 UUID；离线模式可能按玩家名生成 UUID，改名后 UUID 可能变化。代理模式必须确保 UUID 来自可信代理/服务端验证结果。
- 若服务器端允许同名或采用不同大小写规则，应根据实际游戏版本与服务端规则调整名字唯一约束；UUID 唯一约束仍应保留在对应身份域内。

**可见性语义（MVP）**

- `visibility=1`：该角色消息允许进入网站公开消息流，游客和登录用户均可见。
- `visibility=0`：该角色消息不向网站公开访客展示。
- 本设计采用“当前角色设置控制其全部历史消息的公开可见性”：切换为隐身后，该角色历史消息也不再出现在公开消息查询、搜索和推送中；重新公开后，历史消息可重新显示。数据库中的历史消息不因切换而删除。
- 这只是公开可见性规则，不等于匿名发言。隐身角色消息不应以匿名形式继续展示给游客。
- 已发送到客户端的数据无法被远程收回；权限切换后，服务端应停止后续推送并在后续 API 查询中执行新规则。
- 网站游客只能浏览公开消息，不能发送消息；已绑定角色的发言权限仍由后端认证与授权逻辑决定。


### 3.8 `server_message_subscriptions` — QQ 私聊消息订阅

| 字段           | 类型            | 约束 / 默认值                        | 说明           |
| ------------ | ------------- | ------------------------------- | ------------ |
| `id`         | `BIGINT`      | PK, identity                    | 记录 ID        |
| `server_id`  | `BIGINT`      | NOT NULL FK → `game_servers.id` | 被订阅的服务器      |
| `user_id`    | `BIGINT`      | NOT NULL FK → `users.id`        | 订阅者账号        |
| `qq_enabled` | `BOOLEAN`     | NOT NULL DEFAULT TRUE           | 是否启用 QQ 私聊转播 |
| `created_at` | `TIMESTAMPTZ` | NOT NULL DEFAULT `now()`        | 创建时间         |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL DEFAULT `now()`        | 更新时间         |

**索引与约束**

- `FOREIGN KEY (server_id) REFERENCES game_servers(id)`。
- `FOREIGN KEY (user_id) REFERENCES users(id)`。
- `UNIQUE (server_id, user_id)`。

**规则**

- 开启 QQ 私聊订阅要求用户有有效 QQ 绑定；启用时检查 `qq_bindings.status=1`。
- 不在订阅表重复保存 `qq_uin`，发送时通过有效 QQ 绑定关系查询。
- 订阅是用户主动选择的私聊通知，不是群广播。
- 每条待推送消息仍须检查对应角色的当前可见性与用户订阅状态。

### 3.9 `web_sessions` — 网站登录会话

| 字段           | 类型             | 约束 / 默认值                                       | 说明                                                                                  |
| ------------ | -------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------- |
| `id`         | `BIGINT`       | PK, GENERATED BY DEFAULT AS IDENTITY           | 会话记录 ID                                                                             |
| `user_id`    | `BIGINT`       | NOT NULL FK → `users.id` ON DELETE CASCADE     | 所属用户 ID                                                                             |
| `token_hash` | `VARCHAR(64)`  | NOT NULL UNIQUE, CHECK (char_length(token_hash)=64) | Session 凭证原始 Token 的 SHA-256 哈希（十六进制，固定 64 字符）；数据库只存哈希，不存原始 Token                          |
| `device_name`| `VARCHAR(100)` | NULL                                           | 用户可识别的设备名称（用户自填 / 浏览器上报）                                                          |
| `created_at` | `TIMESTAMPTZ`  | NOT NULL DEFAULT `now()`                       | 登录时间                                                                                |
| `expires_at` | `TIMESTAMPTZ`  | NOT NULL                                       | 会话过期时间（由登录时设定的会话有效期决定）                                                            |
| `last_seen_at`| `TIMESTAMPTZ` | NOT NULL DEFAULT `now()`                       | 最近活动时间；每次请求由应用层显式更新，不由数据库自动维护                                                      |
| `revoked_at` | `TIMESTAMPTZ`  | NULL                                           | 会话撤销时间；NULL 表示有效，写入时间表示已撤销                                                             |

**索引与约束**

- `PRIMARY KEY (id)`。
- `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`：用户删除时级联清除其全部会话（会话属鉴权凭证，非审计记录）。
- `UNIQUE (token_hash)`：登录鉴权时服务端用原始 Token 重算 SHA-256，按 `token_hash` 查询会话；只存哈希可降低库泄露后的冒用风险。
- `INDEX (user_id)`：按用户查询会话列表。
- （可选优化）`CREATE INDEX ix_web_sessions_user_id_active ON web_sessions(user_id) WHERE revoked_at IS NULL`，仅索引活跃会话以加速「查询某用户活跃会话」；按需启用，启用后不必再建全量 `INDEX(user_id)`。

**规则**

- 原始 Token 必须通过密码学安全随机源（如 Go `crypto/rand`）生成；数据库只保存其 SHA-256 哈希，绝不保存原始 Token。
- 活跃会话判定：`revoked_at IS NULL AND expires_at > now()`；后台任务可将过期行置 `revoked_at` 仅用于清理/展示，不可依赖定时任务保证安全（与绑定码一致性原则相同）。
- `last_seen_at` 由应用层在每次鉴权请求时显式更新，不为空，也不依赖数据库自动维护。
- 同一用户允许多条有效会话（支持多设备）；「登出全部设备」即对 `user_id` 下所有 `revoked_at IS NULL` 的行写入 `revoked_at`。
- 删除用户（`ON DELETE CASCADE`）会级联清除其全部会话；若业务改为「优先禁用账号」，禁用账号应配合使会话失效的策略（如缩短 `expires_at` 或批量写 `revoked_at`）。

## 4. MongoDB：聊天消息历史

PostgreSQL 负责权限和身份权威数据；MongoDB 存消息正文和历史。消息记录中的 `sender_user_id`、`server_id` 是引用标识，不替代 PostgreSQL 的绑定/权限验证。

### 4.1 集合：`server_messages`

建议使用 MongoDB ObjectId 作为文档 `_id`，并额外保存单调递增或可排序的 `seq`/时间戳字段用于分页。若产品需要稳定的服务器内顺序号，可由后端为每个服务器分配序号；不要假定不同数据库之间的 ID 可直接比较。

| 字段                 | 类型            | 必需 | 说明                                                                          |
| ------------------ | ------------- | -: | --------------------------------------------------------------------------- |
| `_id`              | `ObjectId`    |  是 | 消息唯一 ID                                                                     |
| `server_id`        | `int64`       |  是 | 对应 PostgreSQL `game_servers.id`                                             |
| `seq`              | `int64`       | 建议 | 服务器内消息顺序号，用于稳定游标分页；由后端生成                                                    |
| `sender_type`      | `string`      |  是 | `player`、`system` 等                                                         |
| `sender_user_id`   | `int64/null`  |  否 | 玩家对应网站账号 ID；系统消息为空                                                          |
| `sender_game_name` | `string/null` |  否 | 发送时的游戏名快照，用于历史展示                                                            |
| `sender_game_uuid` | `string/null` | 建议 | 发送时的游戏角色 UUID 快照；建议保存为规范化 UUID 字符串，便于跨存储使用                                  |
| `source_type`      | `string`      |  是 | `game` 或 `web`                                                              |
| `content`          | `string`      |  是 | 消息正文，纯文本为主；服务端需限制长度                                                         |
| `content_format`   | `string`      | 建议 | MVP 使用 `plain`；后续可扩展 `markdown`                                             |
| `visibility_scope` | `string`      |  是 | MVP 建议固定为 `server_public`；真正可见性仍需按当前 `server_game_bindings.visibility` 动态判定 |
| `created_at`       | `Date`        |  是 | 服务端写入时间，UTC                                                                 |
| `edited_at`        | `Date/null`   |  否 | 编辑时间，若 MVP 不支持编辑可不使用                                                        |
| `deleted_at`       | `Date/null`   |  否 | 软删除时间，若 MVP 不支持删除可不使用                                                       |
| `metadata`         | `object/null` |  否 | 来源消息 ID、客户端版本等非敏感扩展元数据                                                      |

**索引建议**

- `{ server_id: 1, seq: -1 }`：主要历史查询和向前翻页。
- `{ server_id: 1, created_at: -1 }`：按时间查询/排序的备用索引。
- `{ sender_user_id: 1, created_at: -1 }`：用户消息历史或管理查询（确有需求时再建）。
- 若 `seq` 不使用，则用 `{ server_id: 1, created_at: -1, _id: -1 }` 作为稳定复合排序与游标条件。

**分页规则**

- 首次拉取：按 `server_id` 查询，按 `seq DESC` 取最近 N 条，再反转结果供客户端按时间正序显示。
- 加载更早历史：使用游标条件 `seq < before_seq`，而不是 `skip/offset`。
- WebSocket 事件携带消息 `_id`、`seq`、`server_id`，前端用 ID 去重。
- `seq` 生成机制必须能处理并发写入；如果不需要严格连续，可接受跳号，但应保持同一服务器内唯一且可排序。

### 4.2 可见性执行

查询消息时，后端应：

1. 验证访问者是否登录；游客允许读取公开消息流。
2. 对玩家消息根据 `sender_user_id + server_id` 查询有效 `server_game_bindings`。
3. 仅当对应绑定有效且 `visibility=1` 时，将消息放入公开结果；系统消息按服务器公开策略处理。
4. WebSocket 推送、历史分页、搜索结果、QQ 私聊订阅都使用相同授权函数/服务，避免某个出口泄露隐身消息。
5. 角色解绑后，是否继续显示历史消息由业务策略决定；MVP 建议解绑角色的历史消息不再作为当前公开玩家消息展示，除非专门定义“解绑后历史保留公开”的规则。

> 说明：若后续需要高性能地按可见性过滤大量历史消息，可考虑在消息中写入发送时的可见性快照。但这会改变“当前设置控制全部历史”的语义，需要另行迁移设计，不能将快照与动态权限混用。

### 4.3 附件与图片（后续阶段）

图片二进制不直接存 PostgreSQL，也不建议把大文件塞进消息文档。图片上传到对象存储（S3 兼容服务等），MongoDB 消息文档中只存附件引用数组，例如：

- `attachments[].object_key`
- `attachments[].mime_type`
- `attachments[].size_bytes`
- `attachments[].width`
- `attachments[].height`
- `attachments[].alt_text`

第一阶段建议文本、Unicode Emoji 和安全的链接；第二阶段再加入图片上传与附件权限校验。Markdown/链接渲染应过滤危险 HTML，避免 XSS。

## 5. Redis：缓存与短期状态

Redis 不作为账号、绑定或消息历史的权威存储。以下为建议键名，实际 TTL 和数据结构可按实现调整。

| Key 模式                                       | 类型             | 用途                         | 生命周期/说明                               |
| -------------------------------------------- | -------------- | -------------------------- | ------------------------------------- |
| `revolcast:server:{server_id}:heartbeat`     | Hash / String  | ~~最近心跳、在线人数、最大人数、MOTD、最后更新时间~~ | **已被下行 `revolcast:server:status:{server_code}` 取代**（未实现过；改用 code 定位以避免查询侧反查 id） |
| `revolcast:ratelimit:{scope}:{subject}`      | String/Counter | 登录、发码、发消息、API 请求限流         | 短 TTL                                 |
| `revolcast:nonce:{server_id}:{nonce}`        | String         | API 签名防重放                  | TTL 覆盖允许的时钟偏差窗口                       |
| `revolcast:bindcode:attempt:{subject}`       | Counter        | 绑定码尝试次数限制                  | 短 TTL；真实绑定码仍以 PostgreSQL 为准           |
| `revolcast:ws:presence:{user_id}`            | String/Hash    | WebSocket 在线状态（如需要）        | TTL + 心跳续期                            |
| `revolcast:cache:server:{server_id}:summary` | Hash/JSON      | 服务器展示信息缓存                  | 可失效重建，不作为权威配置                         |
| `revolcast:cache:server:list:available`      | String (JSON)  | 可用服务器列表（QQ `server list` 指令用） | TTL 300s；`game_servers` 创建/更新/停用后主动 DEL，读失败 fail-open |
| `revolcast:ratelimit:qq:game_bind:{qq_uin}:{server_code}` | Counter | QQ 侧生成游戏角色绑定码的限流（BIZ-009） | 5 分钟 5 次；放在只读幂等校验之后，Redis 故障 fail-open |
| `revolcast:ratelimit:game:redeem:{server_id}:{player_uuid}` | Counter | 游戏内兑换角色绑定码的限流（BIZ-010） | 5 分钟 5 次；**前置计数**（码格式校验后立即计数，用于拦截猜码），Redis 故障 fail-open |
| `revolcast:server:status:{server_code}` | String (JSON) | 服务器在线状态快照：`{server_id, server_code, online, max_players, players[{nickname,uuid}], updated_at, source}`（BIZ-012） | TTL = 3 × 采集周期（默认 180s）；每 60s 由 `send_rcon_command: list uuids` 采集覆盖写入；WS 连接注销时主动 DEL；**可随时重建，非权威数据**，查询侧 fail-closed（Redis 故障回「暂时不可用」） |

不要仅依赖 Redis TTL 实现绑定码一次性消费；PostgreSQL 的原子更新与事务才是权威。在线状态的过期表示“最近未收到心跳”，应展示为未知/过期状态，而非必然判定服务器进程已停止。

## 6. 关键业务事务与一致性

### 6.1 QQ 绑定

1. 用户在机器人私聊中请求绑定码。
2. 机器人服务创建 `qq_bind_codes` 记录，保存 `bot_id`、`qq_uin`、过期时间。
3. 用户登录网站并提交绑定码。
4. 后端在事务中原子消费绑定码。
5. 检查 QQ 当前是否已被其他账号绑定、账号是否已有其他有效 QQ 绑定。
6. 写入 `qq_bindings`，提交事务。
7. 若唯一约束冲突，整个事务回滚并向用户返回明确错误。

> **解绑（BIZ-007）：** 网站侧解绑通过 `POST /api/v1/user/unbind-QQ` 完成，仅校验会话即可执行。解绑在单条原子 UPDATE 中完成（`status` 1→0、`unbound_at=now()`、`updated_at=now()`），不删除历史行；会话解析出的 `user_id` 当前无有效绑定（0 行影响）时返回 409。解绑**不**联动 `server_game_bindings` / `server_message_subscriptions`，也不清理 `qq_bind_codes`（绑定码已在赎回时消费）。

### 6.2 游戏角色绑定

1. 用户在 QQ 私聊发送 `revolcast server <code> bind`（BIZ-009）；后端由该 QQ 的有效 `qq_bindings` 解析出 `user_id`，并校验服务器可用、该账号在该服务器尚无有效角色。
2. 后端生成 `game_bind_codes`，绑定 `server_id` 与 `user_id`（`qq_uin` 仅作审计快照），有效期 10 分钟；同一 `(server_id, user_id)` 同时最多一条待使用码（`ux_game_bind_codes_pending_user`）。
3. 用户在目标游戏服务器内输入绑定码。
4. 游戏端通过受鉴权的 Backend API 提交验证结果和服务器实际观察到的游戏名、UUID。
5. 后端原子消费绑定码，检查账号、服务器状态以及唯一性。
6. 在同一事务中创建 `server_game_bindings`，默认 `visibility=1`（公开）；如产品更重视隐私，可在首次绑定流程中让用户明确选择。
7. 任意约束失败都应回滚；重复 API 请求需通过绑定码状态和幂等处理避免重复创建。

### 6.3 消息写入和推送

1. 后端验证消息来源、服务器身份、玩家绑定状态及发言权限。
2. 将消息写入 MongoDB。
3. 成功持久化后再发布 WebSocket 事件，避免推送成功但历史不存在。
4. 若同时需要通知 QQ 私聊订阅者，建议通过可靠的后台任务/消息队列处理，并在发送前再次检查订阅和当前可见性。
5. 不向 QQ 群自动广播游戏消息，不向 Minecraft 转发 QQ 群消息。

### 6.4 绑定码状态

- 业务判断使用 `status=0 AND expires_at > now()`。
- 后台定时任务可以把过期记录标为 `status=2`，但只用于管理和清理。
- 所有“消费一次”逻辑都必须有数据库条件更新或锁，不允许先查询后无锁更新。

## 7. 约束、权限与安全要求

1. **唯一性由数据库兜底。** 账号名、有效 QQ 绑定、有效游戏角色绑定都必须有唯一索引，不能只靠应用层先查再写。
2. **绑定码一次性消费。** 使用原子条件更新并与关系创建放在同一事务。
3. **密码存储。** 保存专用密码哈希，绝不存明文；优先采用 Argon2id，或按运行环境校准 bcrypt 参数。
4. **服务器鉴权。** Secret 不写日志、不回传；创建时仅展示一次。HMAC 方案需要可安全读取的密钥，而不是不可逆哈希。
5. **API 防重放。** 对服务器回调采用时间戳、nonce 和签名校验；nonce 可用 Redis 短期保存。
6. **消息授权统一。** REST、历史分页、WebSocket、搜索、QQ 私聊推送共用可见性检查。
7. **游客权限。** 游客只能读取公开消息，不能发送消息；前端限制不等于后端授权。
8. **消息正文安全。** 限制最大长度，统一编码；若支持 Markdown，过滤危险 HTML 与 URL scheme。
9. **日志最小化。** 不记录密码、原始绑定码、API Secret；对 QQ 号等个人标识控制日志暴露。
10. **删除策略。** 账号、服务器、绑定关系的删除策略需慎重；优先禁用/解绑并保留必要审计记录，避免级联删除导致消息引用失效。

## 8. MVP 实施顺序

1. PostgreSQL：`users`、`qq_bindings`、`qq_bind_codes`。
2. PostgreSQL：`game_servers`、`game_bind_codes`、`server_game_bindings`。
3. PostgreSQL：`server_groups`（保留群内查询/指令路由用途，但不做自动聊天广播）。
4. MongoDB：`server_messages` 集合与历史游标分页。
5. 统一后端可见性授权服务，覆盖历史 API 与 WebSocket。
6. PostgreSQL：`server_message_subscriptions`，在基础消息链路稳定后实现 QQ 私聊订阅。
7. Redis：限流、心跳缓存、在线状态和防重放 nonce。
8. 后续再做附件/图片、回复、回应、链接预览等能力。

## 9. 需要在实现阶段显式决定的边界

本文为 MVP 提供可实施的基线。以下事项应在编码前落实为 API/产品规则，避免各组件自行解释：

- **隐身默认值：** 本文暂按 `visibility DEFAULT 1`（公开）定义；若优先隐私，应改为默认隐身并在首次绑定时让用户明确选择。
- **解绑后的历史消息：** 本文建议解绑后不再把该角色历史消息当作当前公开玩家消息展示；如要保留公开历史，需单独定义其授权依据。
- **群关联的用途：** `server_groups` 只为机器人群内查询/指令和未来显式分享等功能提供配置，不启用自动游戏聊天广播。
- **消息顺序：** 推荐使用服务器内 `seq` 游标；需确定由单一 Backend 分配还是使用可排序的分布式方案。
- **Minecraft UUID 身份域：** 本文按每个 `server_id` 内 UUID 唯一设计。若多个服务器共享同一可信身份体系，仍建议按服务器隔离绑定；如需跨服统一角色身份，应另建全局角色身份模型。
- **消息编辑/删除：** MVP 可不支持；若支持，应确定审计、软删除和客户端同步规则。
- **跨存储一致性：** PostgreSQL 与 MongoDB 之间没有单一 ACID 事务。消息写入与权限变更应通过清晰的应用流程、幂等机制和必要的后台补偿来协调。
